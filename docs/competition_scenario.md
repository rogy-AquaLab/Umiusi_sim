## sim で測ったこと

すべて `--driver deploy`、cap 0.3、`--start-height 1.0`、seed 1000〜。episode 数が少ない（4〜6）ので
**傾向の比較用**。絶対値は推力・抗力が未較正なので信用しない（`configs/umiusi.yaml` の注記）。

### 1. 旧ハーネスは何も割れていなかった — 原因は 3 つ重なっていた

| 経路 | ≥1 個 | 平均点 |
|---|---|---|
| 旧 `--driver ff`（feed-forward 直結） | 0/4 | 0 |
| `--driver deploy`、割れ判定の速度 0.18 m/s（従来値） | 0/6 | 0 |
| `--driver deploy`、割れ判定 0.05 m/s | **6/6**（初回 中央 18.9 s） | **+88**（赤 1.7 個/回、青 0） |

1. **ff 経路はヨーの符号が逆**: FSM は「+yaw = 機首を body +Z（画像右）へ」を契約にしているが、
   ff は +yaw で −Z へ回る（測定）。的から逃げる向き
2. **アロケータの設定をバンドルから読まないと鉛直推力が出ない**: 純鉛直の力はサーボ ±90° の
   折返し点上にあり、`prefer_deg` / `dead_hold` 無しでは毎ステップ ±90° を往復して、スルー後の
   出力が ~0 になる（測定）。**ライブラリ既定に落ちると実機でも同じことが起きる（A-11 の形）**
3. **割れ判定の速度ゲート**: `MIN_POP_SPEED = 0.18 m/s` は ff 経路の「突進 ~0.5 m/s」に合わせた値。
   実機の経路だと RAM は `RAM_SURGE 0.26 × surge_scale 0.35 = 0.09 m/s`（cap 0.3 の到達上限は
   約 0.21 m/s）で、**ピン先は風船中心から 1〜2 cm まで入っているのに判定されない**（測定）

> ⚠ **3 は sim の問題か実機の問題か分からない。** 押しピンが 0.09 m/s で吊られた風船を割るのか、
> 押しのけるだけなのかは物理の話で、sim では決まらない。**プールで 1 回試すこと**
> （速度を変えて突く。割れなければ RAM を速くする — FSM の `RAM_SURGE` / `surge_scale`）。

### 2. 【実機要確認】navigator のヨー符号で 0 点になる

| ヨーの対応 | ≥1 個 | 平均点 |
|---|---|---|
| FSM の契約どおり（+yaw → 右旋回 = REP-103 で負） | 6/6 | +88 |
| **実機 navigator と同じ**（`+cmd["yaw"]` をそのまま REP-103 の方位目標へ積分 = 左旋回） | **0/6** | **0** |

`sinsei_UMIUSI_autonomy/umiusi_autonomy/umiusi_autonomy/navigator_node.py` の setpoint 経路は
`advance_yaw_setpoint(..., float(cmd["yaw"]), ...)` で、REP-103 の yaw（+ = 左）に**符号を変えずに**
積んでいる。検出器の方位は `+az = 画像右`（`learned_detector.py:172`）。**カメラが正立で前向きなら
実機も的から逃げる。** カメラの取り付け向きで打ち消されている可能性もあるので、sim では断定できない。

**確かめ方（陸上 1 分）**: 風船を画像の右に置いて autonomy を回し、機体が右へ回るか見る。
（control 移植で FSM が core へ行くときも同じ対応表が要る — 移植の前に決着させること）

割れ判定を従来の 0.18 m/s に戻しても中性で **4/4, +128**（RAM が速くなったので判定を満たす）。

#### 効いたもの（単独で入れて切り分け済み）

1. **RAM を実機の速度に合わせる**（`RAM_SURGE 0.26 → 0.6`、`RAM_MAX_STEPS 85 → 200`）— 最大の要因。
   RAM はピン先から約 0.4 m で突入を決めるが、実機の経路では 0.09 m/s しか出ず、1.7 s の打ち切りまでに
   0.15 m しか進まない。中性で割れていたのは「突く → 下がる → 突く」を繰り返して**少しずつ寄る
   ラチェット**だっただけで、姿勢が少し乱れるとそれが崩れる（浮心ずれで全滅した理由）。
   0.6 × `surge_scale 0.35` = 0.21 m/s ≈ cap 0.3 の到達上限
2. **heave をカメラで積分する**（`BalloonBehavior.ki_heave`、新規）— 純浮力 ±1 N を救った。
   FSM の heave は的の仰角に比例するだけで、鉛直は開ループの力なので、残留浮力に逆らうには
   **定常的な仰角誤差が要る**（+1 N でピン先が黄の 13〜29 cm 上に留まり、ALIGN が成立しなかった）。
   積分は**的を実際に観測したフレームだけ**（追跡の保持中は積まない）。学習した値は SEARCH 中も
   足すので、**一度覚えれば的と的の間でも深度を保つ** — 「カメラで補正しながら進む」をそのまま実装したもの。
   **トリム定数ではない**（D-3 と整合）
3. **アロケータの零空間の循環に値段を付ける**（`GeneralAllocator.w_effort`、新規）—
   `prefer_deg` が特異点を避けるために足す「互いに打ち消し合う水平力」が、コストに大きさの項が
   無いせいで `cap_margin × f_max` まで這い上がる。**浮心 0.5 mm ずれただけで 4 基が ±2.1 N で
   押し合い、静止しているのに |duty| 0.265 = cap 0.3 の 88 %**（必要なのは 0.06 N/基）。
   `w_effort 2.0` で 0.055 に落ち、サーボは 60° 付近に留まり、esc の反転は 0。
   **⚠ 実機の B-21「指令 0 でも余計な推力」の一部はこれの可能性がある**（同じバンドル設定で動いている）。
   ただし sim での測定のみ — 実機の `idle_thrust_check.py` で確かめること

**効かなかったもの**: 姿勢の積分 `ki 0.5` — 浮心 10 mm の定常ピッチ 5.4° は 0 にするが、
競技の点は変わらなかった（浮心ずれの失点はピッチではなく RAM のラチェットが崩れることだった）。

### 4. 深度センサ無しで縦をどう持つか

- 残留浮力による鉛直ドリフト（sim の鉛直抗力から）: **10 g で 0.41 m/分、20 g で 0.80 m/分、
  50 g で 1.83 m/分**。鉛直の推力は cap 0.3 で約 0.29 m/s（17 m/分）あるので、**基準さえ見えて
  いれば補正は余裕**。問題は**何も見えていない時間**だけ
- **カメラの縦の視野は ±30°**（`front_cam fovy=60`）。
  - **水面に張り付く** と、赤（2.8 m 下）は水平 **4.9 m 以上**離れないと視野に入らない = ほぼ見えない
  - **床に張り付く** と、赤は 0.5 m、黄は 2.2 m 離れれば見える
  - → 浮く側に外れるほうが**競技的には致命的**。意図して沈める話ではない（D-3 追補: 残差 0 狙い）が、
    「合わせ損ねたときにどちらが痛いか」は非対称
- 今の FSM の SEARCH は heave を**平均 0 の正弦**で振るだけ（`SCAN_HEAVE 0.15`）なので、
  探索中のドリフトには何も逆らわない

**実装した**: `ki_heave`（§3 の 2）。的を追っている間に残留浮力を学習し、SEARCH 中も保持する。

**まだの案**: 的をロックしていない SEARCH 中にも、**見えている風船すべて（青を含む）を高さの目印**
にして学習を続ける。最初の的に届く前に浮き上がって何も見えなくなる場合（スタートが水面のとき）の保険。

## 5. 認識の誤検出・指令追従・周期（2026-10-01 追記）

基準は §3 の推奨構成。**各 8 回**（4 回の結果はばらつきが大きく、順位が入れ替わった）。

### 5-1. 周期 — 一番効くのは認識の周期

実機の実測（`sinsei_UMIUSI_autonomy/docs/performance_tuning.md` §5、フルスタック）:
**姿勢制御 33.8 Hz（50 ではない）/ 認識 5.2 Hz / 画像 12.3 Hz**。

| 1 つだけ実機の値にしたもの | 平均点 | RAM / 回 | 外れ / 回 | **ワイヤの下くぐり / 回** |
|---|---|---|---|---|
| なし（認識 50 Hz・遅延 0・制御 50 Hz） | +131 | 8.6 | 1.4 | 1.2 |
| 制御 33.8 Hz | +115 | | | |
| 認識の遅延 0.2 s | +101 | | | |
| **認識 10 Hz** | **+62** | 13.2 | 5.2 | **7.4** |
| **認識 5 Hz** | **+64** | 11.4 | 2.8 | **7.5** |
| 制御 20 Hz（4 回） | 0/4 で 0 点 | | | |

- **50 → 10 Hz で半減、10 → 5 Hz では変わらない。** 情報量ではなく「間引き」そのものが効いている形
- 失点は最後の約 0.4 m（RAM）に集中: 突進回数と外れが増え、**ワイヤの下をくぐる回数が 6 倍**。
  実機では**絡まりの危険**なので点数以上に重い
- **仮説「保持中の方位が古い」は外れ。** ジャイロで方位を進める `BalloonBehavior.propagate_bearing`
  （新規・既定 off、符号は sim で検証済み）を入れても 10 Hz +62 → +74、5 Hz +64 → +60 で、ほぼ効かない
- 制御は **33.8 Hz なら許容、20 Hz は破綻**

**未解明**: 5〜10 Hz で RAM が外れる仕組み。次に見るのは (1) 近距離で速く変わる仰角が古い
（`propagate_bearing` は方位だけ）、(2) RAM の判定（`PASS_*`）や CONFIRM がフレーム数前提になっていないか

### 5-3. 指令どおりに動くか — `tools/command_tracking.py`（新規）

- 名目のプラントでは surge / heave は**指令どおり**（比 1.00）。飽和は cap 0.3 で surge 0.21 m/s、heave 0.29 m/s
- yaw レートは 0.73〜0.90（P のみのレートループ）

### 5-4. 【重要】推力カーブの指数で姿勢が発振する

保持中に姿勢を小さく蹴ると:

| 実機の指数 \ バンドルの想定 | 2.4 | 2.0 | 1.8 | 1.6 | 1.4 | 1.2 |
|---|---|---|---|---|---|---|
| 現状（想定 2.0、servo-aware 無し） | 0 | 0〜3° | 0〜10° | **14°** | **14°** | **22°**（std、最大 30〜43°） |

- 原因は**サーボの旋回速度**（250°/s）: アロケータは角度を自由に動かし（特に `prefer_deg` の並べ替え）、
  esc は**目標角**向けの大きさを即座に出すので、サーボが回りきるまで力が違う向きを向く。
  サーボを 1000°/s にすると消える。ゲイン（kp/kd）や制御周期では消えない
- **実機の Python ノードも同じ作り**（servo と duty を独立にスルー）。C++ の control の mixer は推定角を使う設計
- 対策（どちらも既定 off）:
  - `DeployDriver(servo_aware=True)`: esc を**サーボが実際に居る角度**への射影で出す → 30〜43° が 7〜13° に
  - **バンドルの指数を低めに置く**（1.6〜1.4）: 実機のほうが急なら鈍くなるだけで安定、平らなら発振、という非対称なので

| バンドルの想定（servo-aware 有り） | 2.4 | 2.0 | 1.8 | 1.6 | 1.4 | 1.2 |
|---|---|---|---|---|---|---|
| 2.0 | 0 | 0 | 0 | 1.3 | 4.1 | 5.5 |
| 1.6 | 0 | 0 | 0 | 0.1 | 3.3 | 4.7 |
| 1.4 | 0.1 | 0 | 0 | 0 | 2.7 | 3.7 |

**指数は今日 IMU だけで測れる**（`tools/exp_from_spin.py`、新規）:
サーボ 0°、純ヨーの符号で duty 0.10 / 0.20 / 0.30 を各 10 秒 → ジャイロの定常ヨーレートを
`--rates 0.10:w1,0.20:w2,0.30:w3` で渡す。sim では真値を誤差 0 で回収。鉛直抗力ではなく**ヨー抗力のモデル**
に依存し、lin/quad の配分が 2 倍ずれても ±0.15〜0.2（1.4 と 2.0 は区別できる）。
**あわせて保持 30 秒の roll/pitch の揺れ**を見れば、発振しているかが直接分かる。

### 5-5. RAM の外れとワイヤくぐりの原因（トレースで特定）

`--trace-events FILE` で RAM ごとの幾何（突入時と最接近時のピン先→風船、体系）とワイヤくぐりを JSONL に出して、
50 Hz と 5 Hz を同じ 8 回で比べた。

| | 50 Hz | 5 Hz |
|---|---|---|
| RAM / 割れた | 69 / 57 | 91 / 35 |
| 外れたのに**ピン先が割れ半径の内側まで入っていた** | 1 / 12 | **42 / 56** |
| 外れの最接近距離（中央） | 0.35 m（途中で中断） | **0.054 m** |
| 突入時の高さずれ（黄 / 赤） | 先端 2.5 cm 高 / 1.9 cm 低 | **5.2 cm 高 / 4.1 cm 低** |
| ワイヤくぐり（うち RAM 中・狙っていた風船自身） | 10 | **60（43・55）** |

**仕組み**: 認識 5 Hz だと縦方向が**進行方向へ行き過ぎる**（登って近づく黄は高く、降りて近づく赤は低く、
4〜5 cm）。ピン先は斜め約 20° で風船の表面に入るが、**sim の割れ判定は「半径に入った瞬間の角度 ≤ 20°」**
なのでそこで弾かれ、中に入ってからは角度が意味を失う（中央 94°）ので二度と割れない。機体はそのまま進んで
**その風船自身のワイヤの下をくぐる**。

| 割れ判定の角度 | 20°（従来） | **35°** | 45° |
|---|---|---|---|
| 認識 50 Hz | +131 | +128 | |
| 認識 5 Hz | +64（くぐり 7.5/回） | **+146（1.0/回）** | +151 |
| 実機の周期（5 Hz・遅延 0.2 s・制御 33.8 Hz） | +54 | **+126** | |
| + 現実の検出器 | +38 | **+60** | |

**結論**: 「認識周期が最大の失点」(§5-1) は**主に sim の割れ判定の産物**。角度を 35° にすると 5 Hz でも 50 Hz 並み。
**実機で決めること: ピンが 20〜30° 斜めに当たって割れるか**（プールで少しずらして 1 回突けば分かる）。
割れないなら縦の行き過ぎを直す必要がある。

**効かなかった対策**（記録のみ、コードには残していない）: RAM 前に「新しいフレームで 2〜3 回続けて中央」を
要求 → 5 Hz で +51 / +46（悪化〜同等）。行き過ぎは RAM の最中に起きている。

**残る主な失点は検出器の質**: 角度 35° でも、recall 0.72 と方位・距離の誤差を入れると +126 → +60

## 2026-10-08: 10/03 較正後のプラントで詰め直し（cap 0.5 = 実機）

| 設定 | 風船 1 個・赤 | 風船 1 個・黄 | 競技場（≥1 個 / 平均点 / 初回 / 赤） |
|---|---|---|---|

A = `--w-effort 2.0 --ki-heave 0.3 --ram-surge 0.6 --ram-max-steps 200 --servo-aware`。追加は `--aim-above-red --search-heave-bias -0.2`
（FSM の `AIM_ABOVE_COLOURS` に red、`SEARCH_HEAVE_BIAS`。どちらも既定は従来どおり）。

- **FSM 既定は cap 0.5 の新プラントで全滅**（突進が届かない）。推奨 A は必須。
- 赤が取れなかった理由は 2 つ: (1) 探索中に深さを保つ仕組みが無く、正浮力（sim +1.2 N）で浮いて 0.5 m の赤が視野の下に外れる（SEARCH 80〜90%）。
  (2) 届いても低い赤の真横〜下から当たり、ピン先が 3 cm まで入っても角度 90° 超で割れない（トレース）。黄と同じく 5° 上を狙うと当たり方が揃う。
- `--search-heave-bias` は機体の浮力トリムに依存する。実機が中性浮力に近ければ −0.2 は潜りすぎ（床へ）。プールで探索中の深さの変化を見て決める。
- 水面が無かった（正浮力で 8 m まで上がる）のはこれまでの全評価に共通の sim の欠陥。これ以前の「水面にいる時間」は当てにならない。

再現: `uv run python -m tools.competition_eval --max-duty 0.5 --episodes 8 --verbose [--layout single --single-colour red --minutes 2] --w-effort 2.0 --ki-heave 0.3 --ram-surge 0.6 --ram-max-steps 200 --servo-aware --aim-above-red --search-heave-bias -0.2`
